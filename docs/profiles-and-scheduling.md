# Gesture profiles and runtime scheduling

## Versioned local profiles

The profile format is `gesture-manager-profile` version 4. Each `%LOCALAPPDATA%\GestureManager\profiles\<profile UUID>` directory contains `profile.json`, `datasets\<gesture UUID>.json`, an optional `models\custom_gestures.json`, and the profile's action settings. The manifest records custom gesture IDs and definitions, safe relative dataset/model references, shortcut mappings, per-gesture SVC decision margins and cooldowns, a `dry_run` preference, nullable `stop_gesture_id`, `pause_gesture_id`, and `resume_gesture_id` values, the `theme_mode` (`light` or `dark`), and creation/update timestamps. Versions 1 through 3 are accepted and normalized to version 4; legacy v1 sidecar settings are migrated when available, and profiles without a theme default to light on first migration. Gesture features and classifier weights remain the same validated numeric JSON formats already documented elsewhere.

The profile's `dry_run` value records the user's selected preference and is included in export/import. If that preference is Real input (`false`), the dispatcher still starts in Dry-run and the app asks for explicit confirmation at startup or after profile activation before enabling real input. Declining leaves the saved preference intact for the next time. Choosing Dry-run saves `true` to that profile. Pause and Resume may refer to the same static custom gesture; a shared gesture toggles between the two states after a release. Stop must refer to a different gesture. Stop is intercepted before ordinary mappings and stops recognition. Pause blocks ordinary shortcut dispatch while leaving recognition active; Resume restores ordinary dispatch. These control gestures use the same confidence, ambiguity, and stable-frame recognition gate as other gestures and are intercepted before mappings. The selected light or dark theme is saved to the active profile and restored whenever that profile is opened.

The first launch creates a **Default** profile by copying the existing local datasets, saved data-only model, and action mappings. Original data files are retained. Profiles created later start empty. Selecting a profile switches Gesture Studio, model loading/training, Actions, and live recognition to that profile's local storage. Editing labels or examples does not modify another profile's files.

Export writes a `.gmp` ZIP containing exactly `profile.json`, referenced feature-only dataset files, and the optional portable model JSON. Model and datasets are bundled, not fetched by path from another machine. Import treats the archive as untrusted: it checks size/count limits, rejects absolute/traversal/backslash paths, symlinks and unlisted members, validates all schemas and numeric bounds, and never extracts outside a temporary directory or interprets a script. Imports install under a profile UUID directory; they do not overwrite the active profile.

## Adaptive runtime scheduling

The current live recognition mode requests 15 inference FPS while the Gesture Manager top-level window is foreground, and 10 FPS while it is not. The unfocused rate stays high enough for shortcut use while a different application has focus. Camera capture requests 15 FPS, so the focused inference target matches its configured capture rate. When ordinary shortcut actions are paused but recognition remains active for Resume and Stop control gestures, the target drops to 2.5 FPS. Windows focus is detected with `GetForegroundWindow` and `GetAncestor(GA_ROOT)` against the Tk window handle. If focus detection is unavailable, the scheduler conservatively chooses 10 FPS. The engine retains its loaded model and changes cadence without reopening it; camera frames remain latest-only, so inference skips stale frames. These are requested targets, not measured guarantees.

Strict pause is the default and stops camera capture, releasing the device. Stopped mode targets 0 FPS and releases the camera. An explicit General Settings opt-in enables paused motion wake: a separate worker captures at 320×240 and 2.5 FPS, downsamples frames to 64×48 grayscale, and checks frame differences. It does not load the hand model or classifier while paused. A motion event stops that camera worker before resuming recognition; the recognition gate still waits for a neutral hand release. No microphone component exists. FPS values are targets; camera/backend behavior, model latency, and hardware can lower actual throughput.

While the runtime is active, the UI samples the newest camera frame once per second and compares a 64×48 grayscale signature. If frame movement stays below the detector's threshold for five minutes, the runtime enters strict Pause and releases the camera. Resume is manual. This heuristic can mistake a very still scene for inactivity or small camera exposure changes for movement; camera frames remain in memory and are not saved. During strict Pause, the adaptive/UI status polls slow to one second and five seconds respectively, and idle recognition workers sleep rather than continuously polling.

## Measured local run

One direct webcam run was performed in this development environment on Windows 11 build 10.0.26300, Python 3.13.7, and a 16-logical-CPU machine. WMI denied access to the processor model, so the exact CPU SKU is not recorded. Settings were camera index 1, 640×480 capture at 15 FPS, LiteRT CPU inference with 2 threads, and the bundled local hand models. No hand was held in view during the measurement. Those measurements were taken with the previous 10 FPS focused / 1 FPS unfocused targets; the faster targets above have not yet been benchmarked.

| Mode | Target / observed inference rate | Process CPU* | Working set | Inference latency |
|---|---:|---:|---:|---:|
| 10 FPS mode (focused target) | 10 / 9.37 FPS over 8 s | 19.9% | 107.0 MB | 4.49 ms, last reported sample |
| 1 FPS mode (unfocused target) | 1 / 1.00 FPS over 5 s | 7.2% in this run; 16.2% in a separate 5 s run | 107.0 MB | 5.72 ms, last reported sample |
| Strict pause | 0 / 0 FPS over 2 s | 0.8% | 103.7 MB | No inference |

The camera opened in 1,393 ms; engine start through first running status took 1.46 s. The 10 FPS target-rate run observed 9.37 FPS. The process had 120 camera frames captured in that interval. Strict pause released the camera and processed no frames during the check. The engine rates were measured directly; foreground-window switching itself was tested with a mocked Win32 API, not during this webcam measurement. These are single-machine, short-run measurements, not performance guarantees. CPU is process CPU time as a percentage of one logical core, not total system utilization. Memory is Windows working set. Results vary with camera backend, lighting, concurrent workload, and device.
